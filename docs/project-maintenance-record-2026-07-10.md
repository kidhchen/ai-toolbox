- 可直接打开的 HTML 工具

- 全部工具

## 5. 投稿和审核流程

### 投稿页面

投稿人只需要提供钉钉文档链接。建议文档按以下基础格式编写：

- 工具名称
- 一句话介绍
- 适合谁使用
- 解决的痛点
- 软件功能
- 核心功能图示
- 安装/使用方法

投稿说明应告诉投稿人：正文尽量写在同步块中，图片、安装包和补充资源放在钉钉文档里，方便后续归档和自动更新。投稿页不开放视频上传，视频由管理员后续处理。

### 隐藏审核入口

本地维护地址：

`http://localhost:4173/index.html?admin=1#/review`

审核页支持：

- 按状态筛选投稿
- 批量通过
- 批量退回
- 归档
- 复制已通过链接

普通公开页面不展示审核入口。审核功能依赖 Supabase 中的表和审核 RPC；如果页面提示“审核口令无效，或审核函数还未配置”，优先确认已执行 `supabase/schema.sql` 以及审核函数 SQL。

审核口令不写入本记录，也不写入 GitHub。

### 通过后的处理原则

投稿通过后，不能只改状态就期待自动生成完整工具页面。管理员还需要：

1. 打开投稿者提供的钉钉文档。
2. 判断是否有可读取的同步块。
3. 有同步块时，在知识库新建同名文档并引用同步块。
4. 没有同步块时，直接把投稿者原文链接作为后续更新依据。
5. 抓取正文、图片和资源入口，去重后写入 `content/tools.seed.json`。
6. 需要时将图片或视频整理到 GitHub 或 Supabase，再替换正式链接。
7. 在本地预览并发布到 GitHub Pages。

## 6. 资源管理原则

### HTML 工具

HTML 工具需要像网页一样直接运行时，优先放在 GitHub Pages 的 `tools/` 目录，例如：

`tools/instant-sound-effects-5.html`

站内入口使用该 GitHub Pages 地址，而不是直接把 HTML 文件当作 Supabase 下载文件。

### 图片

- 用户提供的高清原图优先保存到仓库或正式资源存储。
- 详情页中图片按正文顺序展示。
- 封面选择最能代表工具工作界面的图片。
- 图片需要避免使用低清缩略图或即将过期的钉钉临时 URL。

### 视频

- 投稿页不开放视频上传。
- 视频由管理员审核后决定是否上传 Supabase Storage。
- 视频格式优先 `.webm`，兼容性需要时再提供 `.mp4`。
- 视频必须放在正文对应位置，不能统一放到页面最底部。
- 白天版 Hero 视频使用循环播放；夜晚版不使用这套视频底图。

### 安装包

- 大型安装包原则上让用户从钉钉原文下载，减少 Supabase Storage 压力。
- 只有确定需要站内下载时，才上传到 Supabase Storage。
- 不要把钉钉临时签名 URL 固化到网站数据中。

## 7. 发布流程

日常更新流程：

1. 修改 `content/tools.seed.json`、`assets/app.js` 或相关资源。
2. 本地启动预览服务并检查首页、详情页和夜晚/白天主题。
3. 检查图片、视频和 HTML 链接是否可访问。
4. 通过 GitHub Desktop 提交修改。
5. 点击 `Push origin`。
6. 等待 GitHub Pages 部署完成，再用无痕窗口检查缓存后的正式页面。

## 10. 重要注意事项

- 修改后必须确认是从本地预览服务访问，不要直接双击 `index.html`，否则可能出现“请通过本地预览服务打开网站”。
- GitHub Pages 是静态发布，代码和种子内容的更新需要重新 Push。
- Supabase 的动态数据和 GitHub Pages 的静态内容是两套系统，修改 Supabase 不会自动改写 `content/tools.seed.json`。
- 钉钉文档能否抓取图片和正文，取决于权限、同步块类型和接口返回内容。
- 临时资源 URL 可能过期，不能直接作为长期站内资源。
- 公开网页中的前端配置不能保存管理员密钥。
- 发布前保留 GitHub 提交记录，不要使用破坏性 Git 操作覆盖用户已有修改。
